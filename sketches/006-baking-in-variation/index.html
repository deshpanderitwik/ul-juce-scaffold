Baking variation into a drum pattern

Sketch 006 — what shape does the data structure need so variation is first-class?

What separates a good drum pattern from a great one is usually variation the tools don't make easy to bake in. Most DAWs ship a flat 16-step matrix that loops identically forever; everything past that is bolted on (clone the pattern and edit, parallel automation lanes, drum-rack macros). This sketch lays out the design space and proposes a shape.

Six flavors of variation

Fills
Pattern changes for a bar or part-bar at structural moments — every 4th bar, the bar before a section transition.
Per-cycle micro-variation
Same pattern, each loop slightly different — a ghost snare here, a dropped hat there. Keeps the loop from sounding frozen.
Accent / velocity breathing
Same hits, but dynamics shift across the phrase — a hat crescendoing across 4 bars, an accent that walks.
Timbral substitution
Open vs closed hat, rim vs centre snare, kick pitch wobble. Same slot, different sample.
Conditional events
"Only every 4th cycle." "Only if last bar's snare landed." Patterns that respond to their own history.
Phrase architecture
2/4/8-bar phrases that evolve rather than repeat. The natural unit of drummer-thought.

How existing tools represent it

Boolean matrix + automation lanes
The DAW default. Variation lives in parallel tracks. Powerful, but external to the pattern object.
Stochastic cells
Each cell is a distribution. Variation comes for free, but determinism is gone — no clean "fill on bar 4".
Multi-pattern + selector
Several patterns + a rule that picks which is live. Variation is real but lives above the pattern, in song mode.
Pattern-as-function (Tidal)
every 3 (fast 2) $ bd*4. Composition gives a huge ceiling but doesn't map cleanly to a visual UI.
Parameter locks + trig conditions (Elektron)
Each cell carries state + per-cell overrides + a condition (1:2, 50%, NEI) deciding whether it fires. Variation baked into the cell itself.

The proposed shape

Synthesizing: make the phrase the natural unit, and make variation a scoped conditional modulation of a base skeleton.

type Pattern = {
  phraseLength: number,        // bars (e.g. 4)
  voices: Voice[],
}

type Voice = {
  name: string,
  base: Cell[],                // the skeleton
  variations: Variation[],     // composable mods
}

type Variation = {
  scope:     'cell' | 'beat' | 'bar' | 'voice',
  condition: Expr,             // every(n), p(0.4), barInPhrase==3,
                               //   prevHit(snare, 9), ...
  effect: {
    set?:    Partial<Cell>,    // override velocity / pitch / length
    add?:    Cell[],           // grace notes, ratchets
    remove?: CellRef[],        // drop a hit
    shift?:  number,           // micro-offset (sub-step)
    swap?:   Sample,           // closed → open hat
  }
}

Five invariants worth pinning:

  1. Variation is data, not external automation — it lives inside the pattern.
  2. Variations are scoped and named — you can toggle them like layers.
  3. They compose — several can stack on the same cell; resolution order is defined.
  4. The base is preserved — switch all variations off and the skeleton survives.
  5. The unit is the phrase, not the bar.

What Elektron got right

Per-cell conditions made conditionality local rather than per-pattern. That single design choice is responsible for most of the perceived aliveness of beats made on those boxes. It's deceptively small and almost no software DAW has internalized it.

The unresolved problem

The data structure is the easy part. The hard part is the UI: how do you surface scope + condition + effect on every cell without drowning the user in menus? Elektron solves it in hardware — a dedicated condition button per cell. On a screen we need invented visual vocabulary that reads at a glance. That's the real design surface for the next experiment.
